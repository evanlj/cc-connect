# 2026-03-24 Squad计划不通过重做方案功能说明

## 背景

原有 Squad 流程在“计划待确认”阶段只有通过命令：`/squad approve-plan <run_id>`。  
当用户认为计划不通过时，只能手动 `stop + start` 新 run，成本高且会打断上下文。

为此新增“计划重做”能力：允许在同一个 run 下提交“不通过原因与重做方向”，让 Planner 直接重出新计划。

## 功能摘要

### 新增命令

- `/squad replan <run_id> <不通过原因与重做方向>`

### 生效阶段（硬门禁）

- 仅在 `wait_plan_approval` 且 `plan_approved=false` 时可用
- 若计划已确认进入执行流程，拒绝重做（提示新建 run）

### 重做动作

1. 保存用户重做说明到 `plan_rework_note`
2. 重置旧计划与任务推进状态
3. 将 run 置为 `planning/running`
4. 重新触发 Planner 生成新计划

## 代码改动

文件：`core/squad_parse.go`

  - 缺少说明时提示填写“重做方向”

## 使用说明

1. 计划出来后先看：
   - `/squad show-plan <run_id>`
2. 若不通过：
   - `/squad replan <run_id> <不通过原因与重做方向>`
3. 新计划生成后再确认：
   - `/squad approve-plan <run_id>`

## 风险与回滚

### 风险

- 重做计划会重置当前 run 的计划快照与任务推进状态（但 run_id 不变）。
- 阶段门禁较严格，执行阶段不支持 replan（避免状态混乱）。

## 2026-03-24 补充修复：replan 后卡在 planning

### 现象

- 执行 `/squad replan ...` 后，run 状态变为 `status=running, phase=planning`，但长时间没有新计划输出。

### 根因

- Runner 主流程中，`phase=planning && plan_approved=false` 缺少执行分支。
- `runSquad` 在该状态下直接返回，导致不会再次调用 Planner。

### 修复点

1. `core/squad_runner.go`
   - 新增 `phase 2.5` 分支：
     - 当 `phase=planning && !plan_approved` 时，直接执行 `runSquadPlanning`。

2. `core/engine_squad.go`
   - `replan` 门禁放宽到 `wait_plan_approval/planning`，便于恢复卡住 run。
   - 在触发 `startSquadRunner` 前先调用 `stopSquadRunner`，避免陈旧 runner 标记导致新 runner 不启动。

3. 测试补充
   - `TestCmdSquadReplan_AllowWhenAlreadyPlanning` 覆盖“已在 planning 阶段再次 replan”的可恢复路径。
